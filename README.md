# RengaHeat — плагин гидравлического расчёта отопления для Renga

Инженерный модуль полного цикла для проектирования водяных систем отопления в
Renga Professional: читает модель, разбирает структуру сети, проверяет её на ошибки,
строит расчётную гидравлическую схему, считает расходы и потери давления, находит
критическое кольцо, балансирует кольца, подбирает диаметры труб, арматуру и насос,
формирует отчёты и — только после предпросмотра и подтверждения — безопасно
записывает результаты обратно в Renga с поддержкой отмены.

Плагин параметрический: он не привязан к фиксированным именам свойств, стилям или
библиотекам. Первый профиль требований — раздел отопления ЧТУ жилого квартала в
Новосаратовке — задан как **данные**, а не как жёстко зашитая логика, поэтому
конфигурация переносима на другой корпус и объект.

> **Важно.** Расчёт RengaHeat не является юридической заменой обязательного
> гидравлического расчёта в Sankom/DCad и согласования производителя арматуры,
> предусмотренных ЧТУ. Плагин формирует прозрачный пакет данных для сверки, экспорта
> и согласования, пока эквивалентность методик не подтверждена.

## Что реально собрано и проверено

- **`RengaHeat.Core`** — расчётное ядро на C# / .NET 8, полностью независимое от Renga
  и COM. Собирается без предупреждений, покрыто тестами.
- **`RengaHeat.Core.Tests`** — 56 тестов (xUnit), все проходят. Покрывают формулы
  гидравлики, узловой решатель, топологию, параметризацию с журналом происхождения,
  классификатор, правила, проверки ЧТУ и полный прогон сессии на типовых схемах из ТЗ.
- **`RengaHeat.Cli`** — демонстрационный прогон ядра без Renga: строит типовую
  двухтрубную секцию, выполняет расчёт под профилем ЧТУ и печатает отчёты и предпросмотр.
- **`RengaHeat.RengaPlugin`** — Renga-адаптер и точка входа плагина (`IPlugin`), `.rndesc`.
  Требует установленного Renga SDK, поэтому **намеренно не включён в основной solution**
  и собирается отдельно (см. ниже).

Проверка в этой среде:

```bash
dotnet build   RengaHeat.sln -c Release      # ядро + CLI + тесты — 0 ошибок, 0 предупреждений
dotnet test    tests/RengaHeat.Core.Tests -c Release   # Passed: 56, Failed: 0
dotnet run --project src/RengaHeat.Cli -c Release       # демонстрационный расчёт
```

## Архитектура

Строгое разделение слоёв — расчётное ядро отделено от COM API, UI и Renga-адаптера:

```
RengaHeat.Core (нет зависимостей от Renga)
├─ Units/            Единицы, размерности, преобразования (Quantity, UnitRegistry)
├─ Model/            Модель сети: NetworkObject, Port, роли, HeatingModel, ModelBuilder
├─ Mapping/          Универсальная параметризация:
│                      FieldDefinition (поля), 12 типов источников значений,
│                      ValueResolver с резервными цепочками, преобразованием единиц,
│                      правилами пустого/нулевого/диапазона и журналом происхождения;
│                      FormulaEvaluator (формулы без внешних зависимостей)
├─ Classification/   Классификатор ролей по правилам (тип/стиль/DN/regex/порты/ОВ_Роль),
│                      приоритеты и конфликты
├─ Rules/            Конструктор правил «Кому → Условие → Что сделать», лимиты,
│                      фиксация DN/арматуры, ручные исключения с журналом
├─ Topology/         Ненаправленный граф связности → расчётный направленный граф;
│                      определение сторон (подача/обратка) по приоритетам, уровни
│                      уверенности, фрагменты, несколько источников
├─ Hydraulics/       Свойства воды; Darcy–Weisbach; трение (Черчилль/Кольбрук/Альтшуль);
│                      узловой решатель колец (направление = знак расхода);
│                      подбор DN по каталогу, балансировка + преднастройка n + авторитет,
│                      подбор насоса
├─ Catalogs/         Каталоги труб/клапанов/насосов с метаданными версий и CSV-импортом
├─ Profiles/         Профиль требований (ЧТУ) как данные; профиль Новосаратовки;
│                      генерация правил из лимитов профиля
├─ Validation/       Проверка модели и требований ЧТУ; Finding со статусами
├─ Calculation/      Оркестрация: построение расчётной схемы (union-find по портам),
│                      CalculationEngine, сценарии, CalculationSession (воспроизводимость),
│                      ChangeSet (предпросмотр изменений), SessionFactory
├─ Reporting/        Ведомости CSV, печатный отчёт, отчёт проверки, пакет сверки Sankom/DCad
└─ Adapter/          IModelGateway (граница с источником данных) + InMemoryModelGateway

RengaHeat.RengaPlugin (зависит от Renga SDK, собирается отдельно)
├─ RengaModelGateway  Чтение модели и применение изменений в операции проекта (Undo)
├─ Plugin             Точка входа Renga.IPlugin, регистрация команды
└─ RengaHeat.rndesc   Дескриптор плагина
```

Ключевые принципы (соответствуют критериям качества ТЗ):

- **Никаких жёстко зашитых имён свойств.** Значение любого поля берётся через
  «Сопоставление»: инженер выбирает объекты, источник (12 типов), конкретное свойство,
  резервные источники, единицу, диапазон и действие при отсутствии. Хранится устойчивый
  GUID свойства, а не имя — переименование не разрушает настройку.
- **Объяснимость.** Каждое значение сопровождается записью журнала происхождения;
  команда «Почему это значение?» выдаёт `объект → роль → правило → источник → исходное
  значение → преобразование → результат`.
- **Ошибочная стрелка трассы не ломает расчёт.** Направление определяется не стрелкой
  Renga, а топологией и знаком расчётного расхода в решателе. Отрицательный расход —
  сигнал о противоположном направлении, а не ошибка.
- **Безопасность модели.** По умолчанию режим «только анализ». Любые изменения проходят
  через таблицу предпросмотра (`ChangeSet`) и применяются лишь после подтверждения,
  в одной операции проекта с Undo. Необратимых изменений нет.
- **Воспроизводимость.** Каждый прогон фиксирует версию ядра, профиль, каталоги,
  сценарий и допущения (`CalculationProvenance`).
- **Готовность.** Сеть с критической неоднозначностью или ошибками не получает статус
  «готово» (`SessionOutcome.IsReady`).

## Что требует установленного Renga SDK или входного `.rnp`

Ядро, тесты и CLI работают **без Renga**. Для реального плагина нужны:

1. **Renga Professional + Renga SDK** (Windows). Уточните по вашей версии: имя
   управляемой сборки API (`Renga.NET.dll`), целевой фреймворк (`net48`/`net6`/`net8`),
   версию API для `.rndesc`.
2. **Проверка сигнатур API** в `RengaModelGateway` и `Plugin` — они написаны по типовой
   модели Renga API (объекты, свойства, параметры, количества, соединительные точки,
   `IOperation` для Undo). Точные имена методов/enum'ов сверьте с установленным SDK
   (помечено комментариями в коде).
3. **Входной `.rnp`** реального корпуса — для чтения фактической модели.

## Как подключить плагин в Renga

1. На машине с Renga SDK соберите адаптер:
   ```bash
   dotnet build src/RengaHeat.RengaPlugin/RengaHeat.RengaPlugin.csproj -c Release \
     -p:RengaSdkDir="C:\Program Files\Renga\SDK"
   ```
   (или задайте переменную окружения `RENGA_SDK_DIR`).
2. Скопируйте `RengaHeat.RengaPlugin.dll`, `RengaHeat.Core.dll` и `RengaHeat.rndesc`
   в папку плагинов Renga (обычно `%APPDATA%\Renga\Plugins\RengaHeat\` — уточните по
   документации версии).
3. Запустите Renga, включите плагин, откройте проект и вызовите команду
   «Гидравлический расчёт отопления».

## Порядок работы в плагине (разделы интерфейса)

Панель проекта → Профиль ЧТУ и правила → Исходные данные и сопоставление →
Классификатор объектов → Каталоги → Схема и направления → Проверка модели → Расчёт →
Подбор → Балансировка → Предпросмотр изменений → Отчёты и экспорт → Версии, сценарии
и журнал. Ядро уже отдаёт данные для всех разделов; UI-диалог собирается поверх
`SessionOutcome`.

## Какие данные нужны для запуска на реальном корпусе

1. `.rnp`-файл корпуса (или доступ к открытому проекту в Renga).
2. Настройка «Сопоставления»: из каких свойств/количеств Renga брать тепловую нагрузку
   приборов, длины участков, диаметры, Kv арматуры (имена свойств вашей модели).
3. Реальные каталоги производителей (трубы, балансировочные клапаны, насосы) — импорт
   CSV вместо встроенных типовых каталогов; согласование арматуры по ЧТУ.
4. Уточнение профиля под объект, если требования отличаются от Новосаратовки
   (зоны, лимиты, серии труб, температурные графики).
5. Ручное назначение сомнительных ролей/направлений (через `ОВ_Роль` или UI), если
   классификатор сообщает о неоднозначностях.
